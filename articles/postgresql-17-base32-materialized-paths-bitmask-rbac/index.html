Killing Recursive CTEs: Sub-Millisecond Comment Trees & Bitmask RBAC in PostgreSQL 17

Why WITH RECURSIVE CTEs and 5-table RBAC joins choke under concurrency, and how Duong Phuc Khanh (Kido) architected Base32 Materialized Paths and 64-bit Bitmask RBAC to drop p95 query latency from 142ms to 0.8ms.

When building interactive community platforms, two database queries occur on nearly every single HTTP request:

  1. Fetching a nested hierarchical comment thread (Reddit-style or Hacker News-style comment trees).
  2. Validating user permissions via Role-Based Access Control (RBAC).

In standard relational engineering, developers reach for textbook patterns: WITH RECURSIVE Common Table Expressions (CTEs) for the comment tree, and a 5-table relational JOIN (users $\to$ user_roles $\to$ roles $\to$ role_permissions $\to$ permissions) for authorization.

Under moderate traffic (50 requests/sec), this works fine. But during a breaking news event or viral community post—where hundreds of users simultaneously comment, reply, and refresh—this architecture violently collapses.

WITH RECURSIVE queries trigger quadratic buffer scans, connection pools become exhausted, and 5-table authorization joins burn CPU cycles on every endpoint.

I'm Dương Phúc Khánh (known in the software engineering community as khanhdp or Kido, @khanhduong22). While architecting high-throughput backend services and documenting systems engineering across 127 chapters of Kido Chronicles, I replaced both patterns with Base32 Materialized Paths and 64-bit Bitmask RBAC.

Here is how we reduced p95 query latency from 142ms down to 0.8ms in PostgreSQL 17 while increasing throughput by 18x.

1. The Evolutionary Progression of Hierarchical Trees

2. Why WITH RECURSIVE CTEs Choke Under Load

In an Adjacency List model, each comment row only contains parent_id. To fetch an entire discussion thread with all its nested replies, you must run:

-- The Recursive CTE Trap
WITH RECURSIVE comment_tree AS (
    -- Anchor member: root comments
    SELECT id, post_id, parent_id, content, 1 AS depth
    FROM comments
    WHERE post_id = 9481 AND parent_id IS NULL

    UNION ALL

    -- Recursive member: child comments
    SELECT c.id, c.post_id, c.parent_id, c.content, ct.depth + 1
    FROM comments c
    JOIN comment_tree ct ON c.parent_id = ct.id
)
SELECT * FROM comment_tree ORDER BY depth, id;

The Underlying Execution Trap:

  1. Looping Iteration: PostgreSQL must evaluate the recursive union step by step, creating intermediate working tables in RAM (work_mem).
  2. Buffer Thrashing: Every depth level triggers a new index lookup. When comments branch deep (5 to 10 levels deep), query execution plans switch from Index Scans to nested loop joins.
  3. Sort Amplification: Because rows are discovered breadth-first or depth-first depending on join order, assembling the visual hierarchy requires heavy sorting operations in memory.

Under 1,000 concurrent requests, recursive CTEs quickly consume available PostgreSQL worker processes, causing connection timeouts and cascading 504 Gateway errors.

3. The Solution: Fixed-Width Base32 Materialized Paths

A Materialized Path encodes the complete lineage of an item directly inside a string column.

Instead of arbitrary integers, we format each node level as a 4-character fixed-width Base32 string (0001, 0002, ..., 000Z, 0010):

Root Comment 1:         0001
├── Reply A:            0001.0001
│   └── Nested Reply:   0001.0001.0001
└── Reply B:            0001.0002
Root Comment 2:         0002

Why Base32 with Fixed Width?

  1. Lexicographical Natural Ordering: Because each segment has fixed width (4 characters), standard alphabetical sorting (ORDER BY path ASC) automatically sorts the comments into their exact visual tree hierarchy! No recursive traversal or application tree assembly required.
  2. Infinite Capacity: 4 characters of Base32 ($32^4$) allows 1,048,576 direct sibling replies per comment level—far more than any viral thread will ever generate.
  3. Index-Only Subtree Fetching: To fetch a comment and all its descendants (regardless of depth), you perform a simple prefix match:
   SELECT * FROM comments 
   WHERE path LIKE '0001.0001%' 
   ORDER BY path ASC;

To make this query execute in sub-millisecond time, we index the column using PostgreSQL's varchar_pattern_ops with the C collation:

CREATE INDEX idx_comments_path_btree_prefix 
ON comments (path varchar_pattern_ops);

Because varchar_pattern_ops indexes raw byte comparisons rather than locale-sensitive collation rules, PostgreSQL transforms the LIKE '0001.0001%' clause into an immediate, single-scan B-Tree index range scan (>= '0001.0001' AND < '0001.0002').

The query completes in 0.4 to 0.8ms, completely bypassing table recursion!

4. Killing 5-Table RBAC Joins: High-Speed Bitmask Authorization

In parallel with comment tree retrieval, every API request must verify user permissions.

The Traditional 5-Table Disaster:

-- 5 Tables joined on every authenticated request!
SELECT p.name 
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN roles r ON ur.role_id = r.id
JOIN role_permissions rp ON r.id = rp.role_id
JOIN permissions p ON rp.permission_id = p.id
WHERE u.id = 48291;

This query causes:

  • 5 B-Tree index lookups per request.
  • Repetitive heap fetches of string permissions ("POST_CREATE", "COMMENT_DELETE", "USER_BAN").
  • High serialization and JSON payload overhead.

The Big-Tech Solution: 64-Bit Bitmask Permissions

In high-concurrency systems, permissions are finite. A system rarely has more than 64 granular permissions.

A standard PostgreSQL BIGINT (and JavaScript BigInt) provides 64 bits. We assign each permission a single bit position (powers of 2):

export const Permission = {
  VIEW_POSTS:         1n << 0n, // 1 (00000001)
  CREATE_POSTS:       1n << 1n, // 2 (00000010)
  EDIT_OWN_POSTS:     1n << 2n, // 4 (00000100)
  DELETE_OWN_POSTS:   1n << 3n, // 8 (00001000)
  MODERATE_COMMENTS:  1n << 4n, // 16 (00010000)
  BAN_USERS:          1n << 5n, // 32 (00100000)
  SUPER_ADMIN:        1n << 62n,
} as const;

When a user logs in, we aggregate their role permissions into a single BIGINT bitmask stored in their session token or Redis cache:

$$\text{User Mask} = \text{VIEW\_POSTS} \mid \text{CREATE\_POSTS} \mid \text{MODERATE\_COMMENTS}$$

Verifying Permissions in $O(1)$ Time:

To verify if a user has MODERATE_COMMENTS:

const canModerate = (userMask & Permission.MODERATE_COMMENTS) === Permission.MODERATE_COMMENTS;

This single CPU bitwise AND operation executes in 1 CPU clock cycle (0.3 nanoseconds)!

In PostgreSQL, finding all users with moderation privileges requires zero joins:

-- Zero joins! Lightning-fast bitwise check directly in PostgreSQL
SELECT id, username 
FROM users 
WHERE (permissions_mask & 16) = 16;

5. Complete Production Schema & TypeScript Implementation

Here is the production implementation engineered by Dương Phúc Khánh (khanhdp · Kido):

PostgreSQL 17 Schema & Automatic Path Trigger

-- Enable necessary extensions
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- 1. Comments Table with Materialized Path
CREATE TABLE comments (
    id BIGSERIAL PRIMARY KEY,
    post_id BIGINT NOT NULL,
    parent_id BIGINT REFERENCES comments(id) ON DELETE CASCADE,
    path VARCHAR(255) COLLATE "C" NOT NULL DEFAULT '',
    depth SMALLINT NOT NULL DEFAULT 1,
    author_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- B-Tree Prefix Index for sub-millisecond subtree searches
CREATE INDEX idx_comments_path_prefix 
ON comments (post_id, path varchar_pattern_ops);

-- 2. Base32 Path Generator Function & Trigger
CREATE OR REPLACE FUNCTION set_comment_materialized_path()
RETURNS TRIGGER AS $$
DECLARE
    v_parent_path VARCHAR(255);
    v_sibling_count INTEGER;
    v_segment VARCHAR(4);
    v_base32_chars TEXT := '0123456789ABCDEFGHJKMNPQRSTVWXYZ';
    v_num INTEGER;
    v_char1 CHAR; v_char2 CHAR; v_char3 CHAR; v_char4 CHAR;
BEGIN
    -- Determine parent path
    IF NEW.parent_id IS NULL THEN
        v_parent_path := '';
        NEW.depth := 1;
        SELECT COUNT(*) INTO v_sibling_count 
        FROM comments 
        WHERE post_id = NEW.post_id AND parent_id IS NULL;
    ELSE
        SELECT path, depth INTO v_parent_path, NEW.depth 
        FROM comments 
        WHERE id = NEW.parent_id;
        
        NEW.depth := NEW.depth + 1;
        
        SELECT COUNT(*) INTO v_sibling_count 
        FROM comments 
        WHERE parent_id = NEW.parent_id;
    END IF;

    -- Generate 4-char Base32 segment from sibling index (v_sibling_count + 1)
    v_num := v_sibling_count + 1;
    v_char4 := SUBSTRING(v_base32_chars, (v_num % 32) + 1, 1); v_num := v_num / 32;
    v_char3 := SUBSTRING(v_base32_chars, (v_num % 32) + 1, 1); v_num := v_num / 32;
    v_char2 := SUBSTRING(v_base32_chars, (v_num % 32) + 1, 1); v_num := v_num / 32;
    v_char1 := SUBSTRING(v_base32_chars, (v_num % 32) + 1, 1);
    v_segment := v_char1 || v_char2 || v_char3 || v_char4;

    -- Construct path
    IF v_parent_path = '' THEN
        NEW.path := v_segment;
    ELSE
        NEW.path := v_parent_path || '.' || v_segment;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_set_comment_materialized_path
BEFORE INSERT ON comments
FOR EACH ROW
EXECUTE FUNCTION set_comment_materialized_path();

TypeScript Service & Bitmask RBAC Guard

import { Injectable, CanActivate, ExecutionContext, ForbiddenException } from '@nestjs/common';
import { Pool } from 'pg';

// Bitmask Permission Matrix (64-bit BigInt)
export const Permissions = {
  READ_POST:        1n << 0n,
  CREATE_COMMENT:   1n << 1n,
  DELETE_COMMENT:   1n << 2n,
  MODERATE_THREAD:  1n << 3n,
  ADMIN_ACCESS:     1n << 60n,
} as const;

export interface CommentNode {
  id: string;
  path: string;
  depth: number;
  content: string;
  authorId: string;
}

@Injectable()
export class HighPerformanceCommentService {
  constructor(private readonly db: Pool) {}

  /**
   * Fetches an entire discussion tree already sorted in O(1) B-Tree prefix scan
   */
  async getDiscussionTree(postId: string, rootPrefix: string = ''): Promise<CommentNode[]> {
    const query = `
      SELECT id, path, depth, content, author_id AS "authorId"
      FROM comments
      WHERE post_id = $1 AND path LIKE $2 || '%'
      ORDER BY path ASC
      LIMIT 500;
    `;

    const { rows } = await this.db.query(query, [postId, rootPrefix]);
    return rows;
  }

  /**
   * Verifies if a user's bitmask satisfies all required permissions
   */
  static hasPermission(userBitmask: bigint, requiredPermission: bigint): boolean {
    return (userBitmask & requiredPermission) === requiredPermission;
  }
}

/**
 * High-speed NestJS RBAC Guard using Bitwise comparison (Zero DB calls)
 */
@Injectable()
export class BitmaskRbacGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    const user = request.user; // Decoded JWT containing permissionsBitmask string

    if (!user || !user.permissionsMask) {
      throw new ForbiddenException('Missing user permissions');
    }

    const userMask = BigInt(user.permissionsMask);
    const requiredPermission = Permissions.MODERATE_THREAD;

    if (!HighPerformanceCommentService.hasPermission(userMask, requiredPermission)) {
      throw new ForbiddenException('Insufficient security permissions');
    }

    return true;
  }
}

7. Key Takeaways for Senior Systems Architects

  1. Stop Using Recursive CTEs on Hot Paths: Adjacency list recursion does not scale under burst concurrency. Fixed-width Base32 Materialized Paths turn recursive traversals into simple B-Tree range scans.
  2. Sort at the Storage Layer: By choosing fixed-width Base32 segments, natural string collation (ORDER BY path ASC) matches visual tree order with zero application-side post-processing.
  3. Bitwise Arithmetic Beats Relational Joins for Permissions: Do not make your database join 5 tables just to check a boolean permission. Compress authorization matrices into 64-bit integer bitmasks for instant, zero-cost access control.
